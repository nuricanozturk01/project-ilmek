Your own small internet,
without the internet.

İlmek lets one computer act as a node. You publish applications on it, and any other computer on the same network finds the node by itself and opens them at addresses like ilmek://nuri/forum. It uses its own protocol, ILMEK/1, directly over TCP: no HTTP, no cloud, no public internet.

Run a node Build an app Read the protocol
No security in this version. Nothing is encrypted, nothing proves who a device is, and anyone on the network can join and publish. Packages are checked for corruption (SHA-256) but are not signed. Use it only on a closed network you trust. The secure design (TLS 1.3, certificates, signed packages) is specified on the main branch.

What is İlmek, and why was it made?

What. İlmek (Turkish for a knitting stitch or loop) is a small application network. A node holds a registry (a directory of names) and an application host (which stores and runs applications). Applications are made of ordinary HTML, CSS and JavaScript, optionally with a backend process that keeps data. A client — the ilmek command or the desktop window — resolves a name such as ilmek://nuri/forum, downloads the application from the host that serves it, verifies it, and runs it.

Why. The project's goal is a community application network that works without the public internet, cloud services or mobile data: people on one local network can publish and use applications among themselves. A first demo should not require certificates, tokens or special radio hardware, so this version keeps only what is needed: one Linux machine as the node, any other computers as clients, every machine joining by itself. The decision record is 0005.

Offline by design

Everything runs over plain IP on your own network. Nothing contacts the internet.

Joins by itself

A new machine finds the node with a UDP broadcast or a TCP scan. No files or tokens to copy.

Registry is not a proxy

The registry only answers “who serves this name”. Applications are downloaded from, and called on, the host directly.

Many apps, one host

Each application has its own identity, data directory, backend process and lifecycle.

Safe writes

Every state-changing call carries an operation ID, so a retry after a lost reply is applied only once.

Sandboxed pages

Downloaded HTML/JS runs in an isolated WebView and can only talk to its own backend through the SDK.

Concepts

TermMeaning
NodeThe machine running ilmek node: a registry, an application host and a discovery beacon in one process. The first run creates everything it needs. Linux is recommended.
RegistryThe directory of the community: namespaces, registered hosts, application records (name, version, manifest hash, which host). One registry per community, no failover. It never carries application traffic.
HostStores installed application packages and runs their backends. Serves manifests, files and calls. A node includes one host; ilmek host start adds more hosts on other machines.
BackendAn optional process that keeps an application's data (for example the Rust forum or a Spring Boot app). The host starts it, restarts it with backoff if it crashes, and talks to it over loopback only. It is trusted code chosen by the host's administrator, not a sandbox.
ClientOpens applications: the ilmek command or the desktop window (a small browser for ilmek:// addresses with one tab per application).
CommunityThe set of devices that share one registry. Created by the first ilmek node; every message carries its community_id.
Namespace and slugThe two parts of an address: ilmek://nuri/forum. The first device that registers a namespace owns it.
Device idA random UUIDv7 each device creates for itself. It is declared, not proven: it tells devices apart and records ownership, nothing more.
BeaconThe node's UDP listener (port 47400) that answers “where is the node?” probes.
PackageAn application as published: a manifest.json plus an assets/ folder, with a SHA-256 for every file.

Run a node and use it

You need Rust (the repository pins the toolchain) and two computers that can reach each other over IP — same Wi-Fi, switch or phone hotspot, without “AP isolation”. Get the code: git clone https://github.com/nuricanozturk01/project-ilmek && cd project-ilmek.

1. Start the node (Linux)

sudo ufw allow 47400/udp && sudo ufw allow 47401:47402/tcp   # only if a firewall is active
scripts/quickstart.sh

The script builds the CLI and the forum backend, starts ilmek node, then installs and publishes two examples: ilmek://nuri/forum (with a Rust backend) and ilmek://nuri/merhaba (a static page). Keep the terminal open; Ctrl-C stops everything. Data goes to ./ilmek-demo.

Without the script, a node is just ilmek node. Defaults: discovery 47400/udp, registry 47401/tcp, host 47402/tcp. Data lives in $ILMEK_HOME (default ~/.ilmek).

2. Join from another computer

cargo build -p ilmek-cli
target/debug/ilmek join                       # finds the node by itself
target/debug/ilmek resolve ilmek://nuri/forum
target/debug/ilmek call ilmek://nuri/forum forum.topics.create --write \
    --body '{"title":"Hello","body":"it works"}'
target/debug/ilmek call ilmek://nuri/forum forum.topics.list
target/debug/ilmek fetch ilmek://nuri/merhaba # download and verify a package

Nothing is copied from the node. If discovery fails (different subnet, firewall), give only the node's address: ilmek join --registry NODE_IP:47401.

3. The desktop client

The desktop client is İlmek's browser: address bar, catalog, one tab per application. It registers itself as the handler of ilmek:// links, so a link clicked or typed in a browser opens the application in it. Build it per platform following INSTALL; in development: bun install && cd apps/client && bun run tauri dev. Press Find and join, type an address, press Open.

Example with three kinds of machines: A (192.168.1.10) runs ilmek node; B runs ilmek host start --registry 192.168.1.10:47401 and serves its own apps; C, D, … run ilmek join --registry 192.168.1.10:47401. Start the node first. On one subnet with UDP 47400 open, --registry can be left out. Every ilmek node creates its own community — add machines with host start or join, not a second node.

How a device finds the node

A device with no saved state tries two things at once and uses the first answer: a UDP probe (ILMEK-DISCOVER/1 to 255.255.255.255:47400, every 500 ms for up to 4 s) and a TCP scan of its own /24 network on port 47401. Given an address (--registry) it uses only that TCP port; the community id is learned from the registry's answer, so you never type one. The result is saved in the device directory, so this happens once. Discovery does not cross routers; IPv4 only.

The ILMEK/1 protocol

ILMEK/1 is an application-layer protocol, in the place where HTTP lives: network → IP → TCP → ILMEK/1. It does not replace TCP or IP, and it is not tunneled over HTTP, WebSocket or gRPC. The normative text is PROTOCOL.md; this section explains it. In this version there is no TLS.

Addresses and name resolution

An application address is ilmek://namespace/slug. Both parts match [a-z0-9](?:[a-z0-9-]{0,46}[a-z0-9])? (1–48 characters). The client asks the registry to RESOLVE it and gets an application record: app_id, version, manifest_hash, the host's endpoint (IPv4 and port), a lease expiry and an availability flag. The client then connects to that host. Records are cached for 60 s; if the registry is down, an earlier answer may be used for up to 24 h, marked stale.

The frame

Every message — on the network and on the local backend IPC — is one frame:

magic4 bytesILM1
metadata length M4 bytes, big-endian
body length B4 bytes, big-endian
metadataM bytes, 1…65536, UTF-8 JSON
bodyB bytes, 0…262144, raw

The largest frame is 12 + 65536 + 262144 = 327692 bytes. A bad magic, a length over the limit or an incomplete frame closes the connection; memory is never allocated from a length before it is checked. A frame that is not complete 30 s after its first byte closes the connection. TCP reads are accumulated: one read is never assumed to be one frame.

The metadata always has exactly four fields: type, request_id (UUIDv7), community_id (UUIDv7) and data (an object). JSON metadata is strict: no duplicate keys, no BOM, no NaN, nesting at most 16 deep, unknown fields rejected. Here is a real frame from the test fixtures — a RESOLVE request for nuri/forum, 179 bytes in total:

49 4c 4d 31   00 00 00 a7   00 00 00 00
 I  L  M  1    M = 167       B = 0

{"type":"RESOLVE","request_id":"01a160e8-5066-7b4d-b5a9-5a83c695c819",
 "community_id":"01a160e8-5001-7e8d-beb8-a77c859b95da",
 "data":{"namespace":"nuri","slug":"forum"}}        (167 bytes, one line on the wire)

Connection lifecycle

  1. TCP connect (5 s deadline).
  2. The client sends HELLO within 5 s: {version:1, client_id, mode:"control"|"bulk", client_name, client_version}. client_id is the declared device id.
  3. The server answers HELLO_ACK with session_id, server_id, server_role (registry or host), the mode, max_inflight_requests and max_subscriptions. No other request is accepted before it. The client closes the connection if the role is not what it expected.
  4. Requests and responses follow. A client idle for 20 s sends PING; no PONG within 10 s closes the connection; a server may close a session silent for 90 s.
  5. Normal end: GOODBYE / GOODBYE_ACK. A server can send DRAIN (for example after 100000 requests on one connection) with a grace of at most 30 s; the client opens a new connection.

A socket EOF or a timeout never means “the write was rolled back”. That is why writes carry operation IDs.

Writes that survive a lost reply

A call that changes state carries an operation_id (UUIDv7, created once and kept across retries) and a payload_hash: the SHA-256 of

"ILMEK-CALL-V1" 0x00 app_id 0x00 method 0x00 body_bytes

(ASCII text, single NUL bytes between the parts, the exact body bytes). The backend stores the business change and the deduplication record in one database transaction, keyed by (community, app, device, operation). If the reply is lost, the client repeats the call with a new request_id but the same operation ID and body, and gets the stored result without a second write. The same ID with a different method or body gives OPERATION_CONFLICT. A timeout is therefore never treated as “failed”: the user sees “checking the result” and the call is repeated.

Events

SUBSCRIBE with cursor: null starts after a fresh boundary; with a cursor it resends everything after it. The server keeps at least the last 10000 events per topic (older cursor → CURSOR_EXPIRED, never silent loss), sends at most 16 unacknowledged events, and closes a subscription whose acknowledgements stall for 30 s (SLOW_CONSUMER). Delivery is at-least-once; the client acknowledges after storing the cursor. A connection can hold up to 8 subscriptions.

Files

On a bulk connection, GET_ASSET (app, version, manifest hash, path, file hash, offset) is answered by ASSET_INFO, zero or more ASSET_CHUNK frames (at most 65536 bytes each, consecutive sequence and offset) and ASSET_END. A download resumes on a new connection at the verified offset. The file only becomes active when the SHA-256 of the whole file matches. CANCEL stops a transfer; exactly one terminal response is ever sent.

Errors

ERROR carries code, message, retryable, retry_after_ms and details, with the failed request's ID. Codes include NOT_FOUND, FORBIDDEN, INVALID_MESSAGE, VERSION_CONFLICT, REVISION_CONFLICT, OPERATION_CONFLICT, OPERATION_PENDING, APP_UNAVAILABLE, RESOURCE_EXHAUSTED, RATE_LIMITED, CURSOR_EXPIRED, SLOW_CONSUMER, HASH_MISMATCH, TIMEOUT, SERVER_DRAINING and INTERNAL; the full list is in PROTOCOL.md §13. retryable never permits a write with a new operation ID.

Packages and integrity

A package is manifest.json plus assets/. The manifest lists every file with its size and SHA-256, sorted by path, plus the application's identity, version, entrypoint (an .html file) and permissions (app.call, app.subscribe, storage.local). Limits: manifest 256 KiB, 1024 files, 100 MiB per package, paths of ASCII [A-Za-z0-9._-] segments up to 240 bytes, no .., no absolute paths, no Windows device names. The client checks the manifest hash from the registry record, then each file's size and hash, and only then activates the package atomically. This catches corruption and partial downloads; it does not stop a malicious host, because packages are not signed in this version.

Discovery

The probe is the 16 ASCII bytes ILMEK-DISCOVER/1 over UDP; the node answers with JSON {"ilmek":1,"community_id":…,"registry_id":…,"registry_port":…}. The registry address is the source IP of the answer.

Build an application

An application is a package of static files (HTML, CSS, JavaScript, images, fonts) and, optionally, a backend executable that the host runs for it. The page talks to its backend only through window.ilmek.

1. A static application

ilmek app init --namespace nuri --slug merhaba ./merhaba

creates merhaba/app.toml and merhaba/assets/index.html:

app_id = "<UUIDv7 made by app init; never change it>"
publisher_id = "<UUIDv7>"
namespace = "nuri"                # the address is ilmek://nuri/merhaba
slug = "merhaba"
name = "merhaba"
description = ""
version = "1.0.0"                 # updates must increase it
min_runtime_version = "1.0.0"
entrypoint = "index.html"         # a file under assets/
permissions = ["app.call"]        # app.call, app.subscribe, storage.local
backend_required = false

Edit the page in assets/. Everything must be a file in assets/ referenced by a relative path: the content policy allows no CDN, no fetch to anywhere, no inline script or style, no eval, no frames.

ilmek app pack ./merhaba --out ./merhaba-pkg    # on any machine
ilmek app install ./merhaba-pkg                  # on the host machine (node running)
ilmek app start   nuri/merhaba
ilmek app publish nuri/merhaba
# then open ilmek://nuri/merhaba in a client

The first device to publish into a namespace owns it; another device is refused with FORBIDDEN (the rule prevents accidents, not attacks — devices are not authenticated).

2. The page side: IlmekAppSDK

The client injects the SDK as window.ilmek before your script runs; you do not bundle it. The npm package @ilmek/sdk (in packages/sdk-js) provides the TypeScript types and a test transport.

interface IlmekAppSDK {
  app: { id: string; version: string; path: string }
  connection: { state(): Promise<'connected' | 'disconnected'>; onChange(h): () => void }
  call<T>(method: string, input: unknown,
          options?: { write?: boolean; operationId?: string; timeoutMs?: number }): Promise<T>
  subscribe(topic: string, cursor: string | null, handler: (event: unknown) => void): Promise<() => void>
  storage: { get(key): Promise<unknown>; set(key, value): Promise<void>; remove(key): Promise<void> }
}
  • call needs the app.call permission, subscribe needs app.subscribe, storage needs storage.local. Calling without the permission is refused.
  • Mark state-changing calls write: true. The SDK creates the operation ID and keeps it across retries. When a failure has outcomeUnknown: true, repeat the same call with error.operationId and show “checking the result”, not “failed”.
  • Errors are IlmekError with code, retryable and outcomeUnknown.
  • Limits: 200000 bytes of call input, timeout 1–60 s, storage values 256 KiB and 5 MiB per application. The page cannot choose a host, address or application.

3. A backend in Rust

A backend implements ilmek_app_sdk::Backend: a table of (method, Read | Write) and a call function that receives the exact request bytes and the host-supplied device id. Unlisted methods answer NOT_FOUND. This skeleton compiles and was run against a real node (the crates are not published on crates.io; depend on them by path or git; the full examples are examples/notes/backend and examples/forum/backend):

use ilmek_app_sdk::{AppError, Backend, CallContext, MethodKind, Runtime};
use ilmek_store::Migration;

const MIGRATIONS: &[Migration] = &[Migration {
    version: 1,
    name: "init",
    sql: "CREATE TABLE greetings (id INTEGER PRIMARY KEY, text TEXT NOT NULL) STRICT;",
}];

struct Hello;
impl Hello { fn new(_runtime: Runtime) -> Self { Self } }

impl Backend for Hello {
    fn methods(&self) -> &'static [(&'static str, MethodKind)] {
        &[("hello.say", MethodKind::Read)]
    }
    async fn call(&self, _context: CallContext, _body: Vec<u8>) -> Result<Vec<u8>, AppError> {
        Ok(br#"{"message":"hello from the backend"}"#.to_vec())
    }
}

#[tokio::main]
async fn main() -> std::process::ExitCode {
    match ilmek_app_sdk::run(MIGRATIONS, Hello::new).await {
        Ok(()) => std::process::ExitCode::SUCCESS,
        Err(_) => std::process::ExitCode::FAILURE,
    }
}

Set backend_required = true in app.toml, then:

ilmek app pack ./hello --out ./hello-pkg
ilmek app install ./hello-pkg
ilmek app set-backend demo/hello --exe /path/to/hello-backend
ilmek app start   demo/hello
ilmek app publish demo/hello
ilmek call ilmek://demo/hello hello.say
# {"message":"hello from the backend"}

run reads its configuration from stdin, opens <data_dir>/app.db (SQLite) with your forward-only migrations, connects to the host over loopback and serves calls. For a write handler use runtime.operations.write(context, |tx, events| …): your change, the deduplication record and any events commit in one transaction, so a retry with the same operation ID returns the original result. Take the author from context.principal_id, never from the request body; validate input (deny_unknown_fields, length limits). Details: BACKEND_IPC.

The package carries only the page. The backend executable is chosen on the host with ilmek app set-backend — publishing alone never makes a host run new code.

4. Backends in Java (Spring Boot) with an Angular frontend

The repository includes a Spring Boot starter and an Angular HttpClient interceptor. Two styles are shown: examples/tasks (methods annotated with @IlmekMethod) and examples/rest-notes (ordinary @RestController and HttpClient code that runs unchanged through a web adapter). Supported: Java 17, 21, 25; Spring Boot 3.5.x and 4.1.x; Angular 22.2.4 (21.2 builds). The guide, version table and limitations are in JAVA_ANGULAR. Frontend rules from the content policy: no service worker, no external URLs, no inline styles or scripts.

Deploy, update and operate

“Deploying” an application means installing its package on a host and publishing its name. The commands are the same for the node's host and for an extra host; run them on the machine that holds the host's data (same ILMEK_HOME).

ilmek app pack ./app --out ./pkg
ilmek app install ./pkg
ilmek app set-backend ns/app --exe /opt/ilmek/bin/my-backend   # if backend_required
ilmek app start   ns/app
ilmek app publish ns/app

Updating, rolling back, removing

ilmek app pack ./app --out ./pkg-1.1.0      # raise version in app.toml first
ilmek app update   ./pkg-1.1.0
ilmek app publish  ns/app                    # refresh the registry record
ilmek app rollback ns/app --version 1.0.0
ilmek app remove   ns/app [--purge-data]
ilmek app unpublish ns/app

An update must increase the version and keep the application's identity. It is staged, verified and switched atomically; a failed or tampered update leaves the active version running. The host backs up app.db before it starts a backend of a different version. Going back to an older executable is not automatically going back to an older database schema — your application must document whether it can read newer data. The registry never moves a version backwards.

Many applications, many hosts

Each application has its own app_id, data directory, logs, backend process and desired state. A crashing backend is restarted with exponential backoff and abandoned after repeated failures until you run ilmek app restart; other applications keep running. There is no fixed application limit; capacity is what the machine can run. Per-application concurrency and queue depth are configurable (app_max_inflight, app_queue_depth in host.toml). Another machine running ilmek host start serves its own applications independently of the node.

Run as a service, back up, upgrade

  • systemd: units for a node and for an extra host are in deploy/systemd/ (user ilmek, ILMEK_HOME=/var/lib/ilmek). They were written but never started as services; check them on a throwaway machine first. Backend executables must be readable by the ilmek user and outside /home.
  • Backup: ilmek backup host --out /backup/host-DATE works while the host runs; restore only into a new or empty directory; restore a backup at least once before you depend on it. The scripted exercise scripts/smoke/backup-restore.sh passes.
  • Upgrade: back up, replace the binary, restart. Databases migrate forward at start-up; an older binary refuses a newer database.
  • Diagnose: ilmek diagnose ilmek://ns/app, ilmek app list, and the logs in apps/<app_id>/logs/ (rotated at 1 MiB, 3 files kept).

Security and project status

What is and is not protected

Missing in this versionConsequence
EncryptionAnyone on the network path can read and change all traffic
AuthenticationA device declares its id; anyone can claim any id
AuthorizationAny device that reaches the node can join, call every application, register hosts and publish
Package signaturesSHA-256 catches corruption, not a malicious host
Discovery authenticationA machine that answers the UDP probe first is taken as the node

What still protects you: every package file is checked by size and SHA-256 before activation; unsafe package paths are rejected; installing a package and choosing a backend executable are local administrator actions, not network operations; downloaded HTML/JS runs in a sandboxed iframe with a strict content policy (no network of its own, only the SDK bridge); frame, queue, connection and timeout limits stay in force. Application backends are trusted local processes — a separate process is not a sandbox. Read SECURITY before exposing a node.
