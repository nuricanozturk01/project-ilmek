# Spring Boot + Angular İlmek Starter Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. **Model override: every implementer and reviewer agent for this plan must run on `haiku` (Claude Haiku 5.5), per explicit user instruction.**

**Goal:** Let a developer write an İlmek application backend as a normal Spring Boot app (`@Service` methods, JPA) and its frontend as a normal Angular app, publish both through the existing `ilmek` CLI, and have them run only on the İlmek LAN — unreachable from the public internet, indistinguishable in developer experience from writing an ordinary Spring+Angular app.

**Architecture:** A new pure-Java library (`ilmek-spring-boot-starter`) reimplements the `ILM1` frame codec and backend-IPC contract from `PROTOCOL.md` §16/§5 natively in Java (no JNI/FFI — confirmed with user), exposes it as Spring annotations (`@IlmekMethod`) and a Spring Boot autoconfiguration so the dependency alone wires everything. A new packaging script makes a standard `ng build` output installable as an İlmek app with zero runtime/client changes (confirmed by research the client already supports this). One new example app (`examples/tasks`) proves the whole path end-to-end against the real `ilmek-host`.

**Tech Stack:** Java 21, Gradle (Kotlin DSL), Spring Boot 3.3.x, Jackson, Spring Data JPA, H2 (embedded), JUnit 5; Angular CLI (latest stable), TypeScript; existing Rust `ilmek-host`/`ilmek-cli`/`ilmek-package` unchanged.

**Spec:** This plan has no separate spec file — the Plan Mode design (approved in-session) is the spec of record; its confirmed facts are restated below as Global Constraints.

## Global Constraints

- `ILM1` frame: 4-byte magic `ILM1`, then `metadataLen: u32 BE` (1–65536), then `bodyLen: u32 BE` (0–262144), then metadata JSON, then raw body bytes. No checksum, no encryption. (`PROTOCOL.md:120-136`, `crates/ilmek-protocol/src/frame.rs`)
- Backend IPC uses the *same* frame codec as the network protocol (`PROTOCOL.md:132`) — no IPC-specific variant.
- Metadata envelope is exactly 4 fields: `type`, `request_id`, `community_id`, `data`. Reject unknown fields, duplicate JSON keys, BOM. (`crates/ilmek-protocol/src/strict_json.rs`, `PROTOCOL.md:138-152`)
- Handshake: backend reads `{token, ipc_port, community_id, app_id, data_dir}` JSON from stdin, connects to `127.0.0.1:ipc_port`, sends `IPC_HELLO{token, app_id}`, waits for `IPC_READY{app_id}`. (`PROTOCOL.md:465-466`)
- After `IPC_READY`, the **host** initiates every `IPC_CALL`/`IPC_SUBSCRIBE`; the backend only replies/pushes. (`PROTOCOL.md:467`)
- `IPC_CALL` carries `AppCall` fields (`app_id, client_app_version, method, operation_id, payload_hash`) plus `principal_id` added by the host — **the backend never computes `payload_hash` itself**, it only carries the value through to the dedupe record. (`crates/ilmek-protocol/src/ipc.rs:33-44`, `crates/ilmek-protocol/src/digest.rs:7-39`)
- `principal_id` is host-supplied and **not authenticated** — must not be treated as a security boundary beyond per-device data partitioning. (`PROTOCOL.md:468`, `docs/IPC.md:40,47`)
- Write dedupe is protocol-mandated: same `(principal_id, operation_id)` + same `(method, payload_hash)` → replay stored result without rerunning business logic; same id + different `method`/`payload_hash` → `OPERATION_CONFLICT`; business write + dedupe row + event append commit in one atomic transaction. (`PROTOCOL.md:350-358`, `crates/ilmek-app-sdk/src/dedupe.rs:44-97`)
- Method/topic name grammar: `^[a-z][a-z0-9_.]{0,63}$`. (`crates/ilmek-protocol/src/wire/types.rs:77-97`)
- Event retention floor: ≥10,000 events per topic; cursor is an opaque string ≤512 chars, encoding is implementation-defined. (`PROTOCOL.md:97,287-288`, `crates/ilmek-app-sdk/src/events.rs:16`)
- No storage engine is mandated — any datastore is fine as long as the atomicity guarantee above holds. (`crates/ilmek-store/src/lib.rs:1`)
- **No official IPC byte fixtures exist.** The root `WIRE_EXAMPLES.json` is stale for this branch (wrong hash domain, pre-rename schema) — never reference it. Only `tests/protocol/fixtures/wire_examples.ilmek.json` is authoritative, and it only has network-protocol examples, not IPC ones. Java IPC correctness must be proven by running against the real `ilmek-host`. (`PROTOCOL.md:581`)
- Backend is trusted code; IPC is not a sandbox and does not allow reaching other apps, registry management, file download, or arbitrary socket proxying. (`PROTOCOL.md:474-475`)
- Frontend CSP (`crates/ilmek-runtime/src/assets.rs:15-26`) is a fixed, global, per-manifest-unconfigurable policy — `connect-src 'none'`, scheme-scoped `script-src`/`style-src`, no `'unsafe-inline'`. Do not edit this file to work around an Angular-side problem; exhaust app-side mitigations first and surface any CSP change request separately for approval (CLAUDE.md: security-guarantee changes require approval).
- `ilmek-package`'s manifest/path rules already accept arbitrary nested relative paths with chars in `[A-Za-z0-9._-]`, so standard Angular hashed chunk output needs no packaging-tool changes. (`crates/ilmek-package/src/manifest.rs`, `crates/ilmek-protocol/src/wire/types.rs:382-423`)
- The native shell auto-injects `window.ilmek` (`IlmekAppSDK`) into every served HTML page — a packaged frontend must not bundle or re-inject its own SDK script. (`crates/ilmek-runtime/src/assets.rs:157-177`)

## Review Focus

- **Duplicate JSON keys in incoming metadata** — Jackson's default parser silently keeps the last value; the protocol requires rejection. A handcrafted frame with `{"type":"IPC_READY","type":"IPC_HELLO",...}` must be rejected, not silently accepted as the last key. (Task 2)
- **Oversized/undersized frame lengths at the boundary** — `metadataLen = 0` and `metadataLen = 65537` must both be rejected (the valid range is `1..=65536` inclusive); `bodyLen = 262145` must be rejected; these off-by-one boundaries are exactly where hand-ported code drifts from the Rust source. (Task 1)
- **Write retried with same operation_id but different body** — must produce `OPERATION_CONFLICT`, not silently re-run the business logic or silently replay the first result. A test that calls `tasks.create` twice with the same `operation_id` and two different bodies must assert the side effect (row count) happened exactly once and the second call's error code is `OPERATION_CONFLICT`. (Task 7)
- **Backend crash mid-call** — the host must see `APP_UNAVAILABLE` for in-flight calls and successfully restart the backend; a retried write after restart with the same `operation_id` must still replay correctly (dedupe state survives the process restart because it's in the database, not memory). (Task 13)
- **Unknown/malformed `app.toml` permission string or missing `backend_required`** — not a new concern introduced by this plan (enforced by existing `ilmek-package`/`ilmek-host` code), but the example app's manifest (Task 11) must be checked against the real `ilmek app pack`/`install` pipeline, not assumed correct from reading the schema.
