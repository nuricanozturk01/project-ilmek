# Developing and publishing applications

An application is a package of static files (HTML, CSS, JavaScript, images, fonts) and,
optionally, a backend executable that the host runs for it. Static applications need no backend.
Dynamic applications keep their data in a SQLite database owned by their backend.

All commands below exist in the `ilmek` binary (`cargo build -p ilmek-cli`). The ones used in the
examples were run by `scripts/smoke/*.sh` and `scripts/quickstart.sh`; anything else is marked.
`--config host.toml` is optional everywhere: the default is `<home>/host.toml`, the file `ilmek node`
(or `ilmek host start`) wrote on this machine. Examples in `examples/`: `hello-html` and `announcements` (static),
`forum` and `notes` (with backends, SQLite persistence, writes with operation IDs, events).

## Quick start: add a new application

1. Start a node: `ilmek node` (see [RUN_NODES_AND_CLIENTS](RUN_NODES_AND_CLIENTS.md)).
2. Scaffold: `ilmek app init --namespace <ns> --slug <name> ./<name>` (creates `app.toml` and `assets/index.html`).
3. Write the page in `assets/` (HTML/CSS/JS, or a built Angular app). Talk to the backend only through `window.ilmek`.
4. Need a backend? Pick one:
   - Java (Spring Boot): [starter README](../java/ilmek-spring-boot-starter/README.md), example in [EXAMPLE_TODO_APP](EXAMPLE_TODO_APP.md).
   - Rust: section "A dynamic application (Rust backend)" below.
5. Package and publish: `ilmek app pack <dir> --out <pkg>`, `ilmek app install <pkg>`, `ilmek app set-backend <ns>/<name> --exe <exe>`, `ilmek app start <ns>/<name>`, `ilmek app publish <ns>/<name>`.
6. Open `ilmek://<ns>/<name>` in the desktop client.

## Prerequisites

- A running node (`ilmek node`) or extra host (`ilmek host start`) on the machine where you install.
- A device to publish from. There is nothing to set up: the first `ilmek app publish` joins this
  machine to the community automatically (UDP discovery, or `--registry IP:47401`).
- **Namespaces are first come, first served.** The first device to publish into `nuri` owns it;
  another device is refused with `FORBIDDEN`. (Devices are not authenticated in this branch; the rule
  prevents accidents, not attacks.)

## A static application

```sh
ilmek app init --namespace nuri --slug merhaba ./merhaba
```

creates `merhaba/app.toml` and `merhaba/assets/index.html`. `app.toml` (all fields shown):

```toml
app_id = "<UUIDv7 generated by app init; never changes>"
publisher_id = "<UUIDv7; app init makes one, any value works>"
namespace = "nuri"                # the address is ilmek://nuri/merhaba
slug = "merhaba"
name = "Merhaba"
description = ""
version = "1.0.0"                 # semantic version; updates must increase it
min_runtime_version = "1.0.0"
entrypoint = "index.html"         # a file under assets/
permissions = ["app.call"]        # app.call, app.subscribe, storage.local
backend_required = false
```

Everything the page loads must be in `assets/` and referenced by relative path: the content policy
allows only the page's own files (no CDN, no `fetch` to anywhere, no inline script or style, no
`eval`, no frames). See [SECURITY](SECURITY.md#application-pages-untrusted-htmljs).

```sh
ilmek app pack ./merhaba --out ./merhaba-pkg      # refuses unsafe names
ilmek app install ./merhaba-pkg                    # on the host machine
ilmek app start   nuri/merhaba
ilmek app publish nuri/merhaba
```

`pack` is deterministic (the same source gives the same manifest bytes) and rejects absolute or
`..` paths, symlinks, control characters and unsafe names; it refuses to overwrite an existing output. `install` verifies manifest hash,
file sizes and SHA-256 before it activates anything (there is no signature). Clients then use:

```sh
ilmek resolve  ilmek://nuri/merhaba
ilmek fetch    ilmek://nuri/merhaba --cache ./cache
ilmek diagnose ilmek://nuri/merhaba
```

## The page side: `IlmekAppSDK`

The client injects the SDK as `window.ilmek` before your script runs; you do not bundle it. The
npm package `@ilmek/sdk` (`packages/sdk-js`) provides the TypeScript types and a test transport.

```ts
interface IlmekAppSDK {
  app: { id: string; version: string; path: string }
  connection: { state(): Promise<'connected' | 'disconnected'>; onChange(h): () => void }
  call<T>(method: string, input: unknown, options?: { write?: boolean; operationId?: string; timeoutMs?: number }): Promise<T>
  subscribe(topic: string, cursor: string | null, handler: (event: unknown) => void): Promise<() => void>
  storage: { get(key): Promise<unknown>; set(key, value): Promise<void>; remove(key): Promise<void> }
}
```

- `call` needs `app.call`; `subscribe` needs `app.subscribe`; `storage` needs `storage.local`.
  Calling without the permission is refused by the runtime.
- Mark state-changing calls `write: true`. The SDK generates an operation ID (UUIDv7) and keeps it
  across retries, so a retry after a lost reply cannot post twice. When a failure has
  `outcomeUnknown: true`, repeat the same call, with the same input, using `error.operationId`, and show "outcome being checked", **not** "failed". Never infer a rollback from
  a timeout.
- Errors are `IlmekError` with `code` (`INVALID_MESSAGE`, `NOT_FOUND`, `FORBIDDEN`, `APP_UNAVAILABLE`,
  `RATE_LIMITED`, …), `retryable` and `outcomeUnknown`. `examples/forum/app/assets/app.js` maps them
  to user messages.
- Limits: 200 000 bytes of input, timeout 1–60 s, storage values 256 KiB, 5 MiB per application.
- The page cannot choose a host, address or application; all calls go to its own application.

## A dynamic application (Rust backend)

A backend implements `ilmek_app_sdk::Backend`: a table of `(method, Read | Write)` and a `call`
function that receives the exact request body bytes and the host-verified `principal_id`. Unlisted
methods answer `NOT_FOUND`. Start from `examples/notes/backend` (smaller) or `examples/forum/backend`.

```rust
// main.rs
ilmek_app_sdk::run(MIGRATIONS, MyBackend::new).await
```

`run` reads the start-up configuration from stdin, opens `<data_dir>/app.db` with your forward-only
`MIGRATIONS`, connects to the host over loopback and serves calls. Inside a write handler use
`runtime.operations.write(context, |tx, events| …)`: your business change, the deduplication
record and any events are committed in **one** SQLite transaction, so a retry with the same
operation ID returns the original result, and the same ID with a different body is refused with
`OPERATION_CONFLICT`. Validate input (`deny_unknown_fields`, length limits) and take the author
from `context.principal_id`, never from the body. Details: [IPC](BACKEND_IPC.md).

Put the compiled backend on the host and bind it to the application (an administrator decision):

```sh
ilmek app pack ./forum --out ./forum-pkg
ilmek app install     ./forum-pkg
ilmek app set-backend nuri/forum --exe /opt/ilmek/bin/ilmek-forum-backend
ilmek app start       nuri/forum
ilmek app publish     nuri/forum
ilmek call ilmek://nuri/forum forum.topics.create --write --body '{"title":"Merhaba","body":"…"}'
```

The package carries only the page (and `backend_required = true` in `app.toml`); the backend
executable is chosen by the host's administrator, because the host runs it with its own privileges.
`--accept-version` lets a backend keep serving older client versions.

## Many applications on one host

Each application has its own `app_id`, data directory (`apps/<app_id>/data`), logs, backend process
and desired state. `app start|stop|restart nuri/forum` affect only that application; a crashing
backend is restarted with backoff and then abandoned until restarted by hand, and other
applications keep running (tests: `a_crashing_backend_leaves_other_apps_running_and_recovers`,
`stopping_one_app_makes_only_that_app_unavailable`). There is no fixed number of applications;
capacity is whatever the machine can run. `ilmek app list` shows state, PID and
restart counts. Per-application concurrency and queue depth are bounded (`app_max_inflight`,
`app_queue_depth` in `host.toml`).

A second host is simply another machine running `ilmek host start`: it finds the node, joins and
registers itself, and serves its own applications independently (`scripts/smoke/multi-app.sh`
runs two hosts as two processes).

## Updating, rolling back, removing

```sh
ilmek app pack ./forum --out ./forum-pkg-1.1.0     # bump version in app.toml first
ilmek app update   ./forum-pkg-1.1.0
ilmek app rollback nuri/forum --version 1.0.0
ilmek app remove   nuri/forum [--purge-data]
ilmek app unpublish nuri/forum
```

An update must move the version forward and keep the application identity; it is staged, verified
and switched atomically, and a failed or tampered update leaves the active version running. The
host backs up `app.db` before starting a backend of a different version. Going back to an older
executable is **not** automatically going back to the older database schema: the application
documents whether it can read newer data. `remove` keeps the data directory unless `--purge-data`
is given. After an update, `app publish` refreshes the registry record (the registry never rolls
a version backwards).
